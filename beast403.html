Beast403: proving a 403 bypass before reporting it

Every 403/401 bypass tool draws on the same handful of techniques. The difference that matters is not the payload — it is how strictly a tool verifies that a bypass actually happened. Beast403 is built around that single discipline.

The problem: false positives, not missing techniques

During access-control testing, a 403 or 401 on a protected path is often a misconfiguration away from being reachable. The existing tooling automates the attempt — mangling the path, injecting headers, swapping the protocol or the verb — and most of it decides success from the status code alone. A page that happens to return 200, or a catch-all that answers everything, reads as a bypass that never happened.

The whole category inherits this from one lineage of techniques (Orange Tsai's path-normalization work, and the 4xx-bypass tools built on it). So the real axis of comparison is not which tricks a tool knows — they mostly know the same ones — but how rigorously it confirms a hit. Beast403 was built to move that bar.

Design: one layer decides

The tool is five separated layers. Data flows one way, and only a single layer is ever allowed to issue the verdict, whatever the technique that produced the candidate.

Raw-socket engine

Requests are sent over a raw socket rather than a client library, so a crafted path is delivered exactly as written — no client-side normalization quietly rewrites the bypass before it reaches the server.

Structural fingerprint (SimHash)

The analysis layer does not compare page bytes. It extracts the tag/structure sequence of a response, drops dynamic noise (visible text, numbers, timestamps, JSON values), and reduces what remains to a SimHash. Two pages built from the same template collide to the same fingerprint even when their content differs — so "same page, different data" no longer looks like a new result.

Live per-target oracles

Before firing any candidate, the calibrator builds four reference points for that specific target: the protected page, random non-existent paths (the guaranteed-404 shape), the generic/landing page, and an authorized reference where credentials exist. Because the oracles are built live, they capture that server's actual behaviour instead of an assumption baked into the tool.

Dropping false positives in five stages

A candidate is not accepted because its status code looks good. The verifier walks it through five rejections first:

  1. Disguised block — a page that carries the block's structure but answers 200.
  2. Catch-all — if random paths return the same page, any "bypass" that matches it is meaningless.
  3. Non-existence — matches the guaranteed-404 shape.
  4. Generic page — resolves to the landing/redirect page rather than the protected resource.
  5. Textual refusal — the body still carries block or login language even at 200.

Only a candidate that survives all five, measured against the live oracles, is reported — with the confidence and the reasons recorded, so each verdict is auditable instead of a black box.

Benchmark

Beast403 was measured against a formal benchmark with a direct comparison to nomore403, across multiple server types behind and in front of a WAF, on a test bed with eight deliberately-planted access-control bypasses.

The recall gap, reported not hidden

33% of bypasses were missed, and the cause is known. The misses were responses served as JSON with no HTML tag structure — the structural fingerprint has little to work with, so a real bypass behind a JSON API can be rejected. The fix (a JSON-aware fingerprint) is scoped; until it lands, the number is published with its explanation rather than rounded away. A verification-first tool that hid its own recall gap would be contradicting its own premise.

Planned next: a JSON-aware signature, context-aware bypasses that key off the application's own behaviour, and protocol-level coverage for HTTP/2 and HTTP/3.
